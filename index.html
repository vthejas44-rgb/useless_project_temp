The day

We started with absolutely no idea.

The build started around 8 AM. By 11 AM, after throwing away ideas that were too useful, we finally had something suitably pointless.

08:00 AM — THE VOID

No idea. Zero direction.

We started the hackathon without a solid project idea. We brainstormed, searched, and kept asking the most important question for a useless-project competition: “Is this actually useless?”

If it solves a real problem, reject it.

One of our early ideas came from an Instagram reel about making a matchmaking/marriage-related webpage. It could have been useful — which was exactly the problem.

11:00 AM — FINALLY.

The opposite terminal.

We finally settled on a terminal where selected action commands do the opposite. The idea also connected with a terminal project I had wanted to build for a while.

Sreelakshmi started shaping the UI/UX while I focused on the terminal implementation.

11:00 AM → 12:00 PM — MAKE IT LOOK REAL

First milestone: a terminal-looking webpage.

Before touching the actual terminal, we turned the UI/UX into a working webpage. By around noon, we had the visual shell of Pookie Terminal.

It looked like a terminal. It just wasn't one yet.

12:00–12:30 PM — FUEL

Even useless software needs food.

Quick food break. Then back to making the fake terminal become a real one.

01:00 PM — OKAY, MAKE IT REAL

The webpage became an actual terminal.

An outside suggestion pushed us toward turning the UI into a real terminal rather than stopping at the webpage. I started working on the Python side and the actual terminal behaviour.

The important design decision was to reverse actions, not navigation. Commands such as ls, pwd, and cd remain normal so the terminal is still usable.

~03:00 PM — IT ACTUALLY WORKED

The moment the stupid idea became real.

The terminal was working. It could interact with the real filesystem instead of being just a fake terminal screen.

We tested navigation, file operations, and the opposite-command behaviour. Some mappings worked; a few, including lock/unlock, did not make it into the working set.

Things that broke

Because of course it did.

The journal is not a changelog. These are the moments where the project actually fought back.

THE PINK-SQUARE / CONTROL-CHARACTER INCIDENT

Why is my terminal speaking gibberish?

During testing, terminal formatting/control sequences started appearing as literal characters in the output. Instead of a clean ls, we were getting things that looked like [31m, [0m and other escape-code fragments.

We had to stop building features and clean up the terminal output before moving on.

The real boss fight

The terminal worked.
The server didn't.

~5:00 PMSubmission target. We needed a live link.
ProblemA real terminal needs an underlying machine/server to actually run.

We explored ways to make the real terminal accessible online, including SSH/Codespaces and server options. We ran into access and payment/account limitations and never got a working server in time.

So the real terminal stayed local. The hosted webpage became the thing we could submit.

What we learned

A useless project taught us useful things.

  • A terminal-looking webpage and a real terminal are two very different problems.
  • Keeping navigation normal while reversing actions made the concept much more usable.
  • Terminal output is not just text — control sequences and formatting have to be handled correctly.
  • Getting software to work locally is only part of the problem. Making it accessible online can be a completely separate challenge.
  • Presentation hardware can fail even when the software is working.
We started the day without an idea. We ended it with a terminal that actively disagrees with us.
